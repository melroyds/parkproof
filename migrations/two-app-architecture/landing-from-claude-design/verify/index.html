Verification

Verify a ParkProof evidence record.

Every ParkProof evidence PDF carries a cryptographic signature appendix, and every record can be saved as an evidence file. This page shows anyone, such as a council officer, an insurer, a court clerk or the driver, how to check offline that a record hasn't changed since ParkProof signed it.

Honest framing. A valid signature shows integrity: the signed details and photo fingerprints are exactly what ParkProof signed, at the signed time. It doesn't show that the record is true (the AI could have read the sign wrongly), who was driving, where the car was, or when the car arrived or left, and it doesn't decide what weight the record carries. That's for whoever reviews it.

What you're verifying

A ParkProof record is signed in parts, called links. Link 0 is signed when ParkProof receives the saved record. Each later link, such as the details at parking, condition photos, a proof of payment photo or the departure, is signed when ParkProof receives it, and carries the SHA-256 of the link before it, so the links form a chain. Each link has a payload (the exact text that was signed, including the SHA-256 fingerprints of its photos) and a signature made with ParkProof's private key (ECDSA P-256), which never leaves AWS KMS. The evidence PDF prints every link in its signature appendix. The record's evidence file (a .json file the driver can download from the record in the app) holds the same payloads and signatures, plus the original photos.

The public key needed to check the signatures is published at /parkproof-public-key.pem. Open it in a browser to confirm it loads, then save it.

What you'll need

  • The evidence PDF or the evidence file, from the person producing the record. Checking the photos needs the evidence file.
  • openssl. It comes with macOS and most Linux systems. On Windows, it comes with Git for Windows (Git Bash) or WSL.
  • A few minutes.

Step-by-step

In the PDF, go to the signature appendix at the back. Each link has three blocks: the payload as text, the payload in base64 and the signature in base64. Copy the two base64 blocks of link 0 into files named link0-payload.b64 and link0-sig.b64, then run:

# 1. Decode the payload. base64 -d ignores the PDF's line wrapping.
base64 -d link0-payload.b64 > link0-payload.txt

# 2. Decode the signature.
base64 -d link0-sig.b64 > link0-sig.bin

# 3. Download ParkProof's public key.
curl -O https://www.parkproof.com.au/parkproof-public-key.pem

# 4. Check the signature. Expect "Verified OK".
openssl dgst -sha256 -verify parkproof-public-key.pem \
  -signature link0-sig.bin link0-payload.txt

Do steps 1, 2 and 4 for each link, with its own file names (link1-payload.b64, link1-sig.b64 and so on). Don't copy the readable payload text instead of the base64 block: the PDF wraps long lines, which changes the bytes, and the check fails.

On Windows

In cmd or PowerShell, base64 -d isn't available. Decode with certutil, which comes with Windows, and in PowerShell type curl.exe in place of curl. You can also run every command on this page as written in Git Bash.

certutil -decode link0-payload.b64 link0-payload.txt
certutil -decode link0-sig.b64 link0-sig.bin
curl.exe -O https://www.parkproof.com.au/parkproof-public-key.pem

Check the links are joined in order

Each link after link 0 carries parent_payload_sha256: the SHA-256 of the payload of the link before it. Print the SHA-256 of each payload file and compare it with the next link's value.

# 5. Print the SHA-256 of link 0's payload.
openssl dgst -sha256 link0-payload.txt
# The value after "=" must equal parent_payload_sha256 in link 1.
# Do the same for each link that follows.

If two links share a number (2a and 2b), two devices each added a part at that point. Both name the same link before them.

Check the photos

The signatures cover each photo's SHA-256 fingerprint, not the image itself. The photos printed in the PDF are re-encoded copies, so their bytes never match. To check a photo, use the record's evidence file. It lists each photo under photos, with its sha256, the links that sign it (signed_in) and the original bytes in base64 (bytes_base64). The file's name starts with parkproof-evidence- and the start of the record's ID. These commands call it evidence.json.

# 6. Take the first photo out of the file with jq, a free JSON tool.
jq -r '.photos[0].bytes_base64' evidence.json | base64 -d > photo1.jpg

# 7. Print its SHA-256.
openssl dgst -sha256 photo1.jpg

# 8. See which link and field sign it.
jq '.photos[0].signed_in' evidence.json

The hex value must equal the photo's sha256 inside the signed payload of each link in signed_in: sign_photo_sha256, car_photo_sha256 or ambient_photo_sha256 in link 0, or a sha256 under photos, photo or return_photos in a later link. Check it against the payload you verified, not just the sha256 next to the photo in the file, which isn't signed. Use .photos[1] for the second photo, and so on.

Without jq, open the file in a text editor, copy a photo's bytes_base64 value into a file named photo1.b64, then run base64 -d photo1.b64 > photo1.jpg.

On Windows

On Windows, PowerShell can read the file itself:

$e = Get-Content evidence.json -Raw | ConvertFrom-Json
[IO.File]::WriteAllBytes((Join-Path $PWD 'photo1.jpg'), [Convert]::FromBase64String($e.photos[0].bytes_base64))
certutil -hashfile photo1.jpg SHA256
$e.photos[0].signed_in
The photo check is separate. Verified OK shows the fingerprints in a payload haven't changed. Only re-hashing the original photo shows a photo is the one that was signed. If the hashes differ, that photo isn't the one ParkProof signed, even when the signature check passed. A file with no bytes for a photo (bytes is not_on_this_device, or withheld_permit for a photo of a permit the driver chose not to include) can't be used to check that photo.

Using the evidence file instead of the PDF

The evidence file also holds each link's payload and signature in base64, so you can do steps 1 to 5 without the PDF. Take link 0 out of the file, then run steps 3 to 5 as above:

jq -r '.links[0].canonical_payload_base64' evidence.json | base64 -d > link0-payload.txt
jq -r '.links[0].signature_base64' evidence.json | base64 -d > link0-sig.bin

In PowerShell:

$e = Get-Content evidence.json -Raw | ConvertFrom-Json
[IO.File]::WriteAllBytes((Join-Path $PWD 'link0-payload.txt'), [Convert]::FromBase64String($e.links[0].canonical_payload_base64))
[IO.File]::WriteAllBytes((Join-Path $PWD 'link0-sig.bin'), [Convert]::FromBase64String($e.links[0].signature_base64))

What the result means

Verified PASS

Verified OK: the payload is exactly what ParkProof signed. The details and photo fingerprints in it haven't changed since ParkProof signed them, at the signed_at time inside it. The photos themselves are checked in steps 6 to 8.

Failure FAIL

Verification failure: the payload or the signature isn't what ParkProof signed. The record may have been changed, or a block may have been copied with a mistake. Copy the base64 blocks again in full and retry before drawing conclusions.

Beyond "did the bytes change?"

A successful verification confirms integrity. It does not confirm:

  • That the AI read the sign correctly. The ParkProof scan is a machine read of a parking sign, and machines can be wrong. The verdict text and rules in the record are the AI's best read at scan time, not ground truth.
  • That the photos depict what the person says they depict. A valid signature shows the photo fingerprints haven't changed since ParkProof signed them, and re-hashing shows whether a photo matches its fingerprint. Neither shows the photos were honestly taken.
  • Any legal outcome. Whether the evidence supports an appeal, a refund, or a court case is the reviewer's call. ParkProof is a tool, not a lawyer.
  • Where the car was, when it arrived or left, or who was driving. The location in the record comes from the driver's phone, or the driver typed it in. Times marked as phone times come from the driver's phone, and ParkProof's signing time is when ParkProof received each part.

Why this exists

Most parking apps that produce "evidence" produce a screenshot. A screenshot could have been edited at any point between when it was taken and when it was sent. The cryptographic signature is the difference between "here's what I saw" and "here's what I saw, and anyone can check it hasn't changed since ParkProof signed it."

The public key is published so the check works offline. You don't need to trust ParkProof, contact our servers or run our app. The check can be done years from now, even if ParkProof is no longer running, as long as openssl exists.
